# Iberian Battery 15-Minute Paper

A research paper on how Spain's move to 15-minute electricity prices in 2025 changed what a battery can earn. It compares battery arbitrage value under hourly and 15-minute prices, both with perfect foresight and with a forecast built only from public data (OMIE and ESIOS).

## Price dataset

The `ib15` package downloads OMIE's day-ahead marginal price files and builds the price dataset the paper uses. It covers delivery days from 1 October 2025, the first day of 15-minute day-ahead prices.

Data lives outside the repo. Set `IB15_DATA_DIR` to the data folder, or pass `--data-dir` to each command. The commands refuse to run if neither is set.

```
uv sync
export IB15_DATA_DIR=/path/to/iberian-battery-15min-data
uv run ib15 download omie    # optional: --start YYYY-MM-DD --end YYYY-MM-DD
uv run ib15 build
```

`download omie` saves each day's file unchanged to `$IB15_DATA_DIR/raw/omie/`. It requests one file at a time with a short pause, and uses whichever file version OMIE currently serves (`.1`, `.2`, ...); the version is kept in the file name. OMIE serves only the latest version of a day, so on every run it re-checks each day already downloaded: if the saved version is no longer served, it fetches the newer one, replaces the old file and reports the day as updated. Each response is validated the same way `build` validates files before it is saved; a truncated or malformed response is reported as an error and nothing is written. The default range runs from 2025-10-01 to tomorrow; tomorrow's prices appear around 13:00 Madrid time, so before then it is reported as not published yet. Any other failure is listed at the end and the command exits non-zero.

`build` validates every raw file (period count for the day's length, duplicate periods, dates, prices, gaps between days, more than one version of a day, a series that does not start on 2025-10-01) and stops with an error if anything is wrong. Otherwise it writes to `$IB15_DATA_DIR/dataset/`:

- `prices_15min.parquet`: one row per 15-minute delivery period, with its UTC start, local delivery date, period number, Spanish and Portuguese prices in EUR/MWh, and the OMIE file version.
- `prices_hourly.parquet`: an hourly series constructed as the mean of each hour's four quarter-hours. It is not OMIE's own hourly product.
- `coverage.json`: date range, counts, DST days, days that used a later file version, price summary and the git commit of the build.

## Weather forecasts

`ib15` also downloads archived weather forecasts as they were issued before each day's bid, and joins them to the prices.

```
uv run ib15 download weather    # optional: --start YYYY-MM-DD --end YYYY-MM-DD (UTC dates)
uv run ib15 build weather       # after `ib15 build`
```

The source is Open-Meteo's Previous Runs API (free for non-commercial use, no key). It serves one fixed model, ECMWF IFS 0.25° (`ecmwf_ifs025`), at the `_previous_day2` lead: the forecast made at least 48 hours before each hour. The variables are hourly `temperature_2m` (°C), `wind_speed_100m` (m/s) and `shortwave_radiation` (W/m²). There are ten locations in mainland Spain: Madrid, Barcelona, Valencia, Sevilla, Zaragoza, Burgos, Lugo, Badajoz, Ciudad Real and Albacete. The coordinates are in `src/ib15/weather.py`.

Bids for delivery day D close at 12:00 Madrid time on D-1. Every forecast value used for D comes from a model run that ECMWF had published by about 08:00 UTC on D-1. The newest is the 00 UTC run of D-1, which the late hours of D use through Open-Meteo's interpolation from 3-hourly to hourly values. That is at least two hours before the deadline. The one-day lead (`_previous_day1`) would break this rule. The evidence is under "Method notes" below, and `build weather` checks the rule for every hour.

`download weather` makes one request per location and calendar month and saves each response unchanged to `$IB15_DATA_DIR/raw/openmeteo/` as `<location>.<model>.<start>.<end>.json`. It pauses between requests and validates each response before saving it. A month is skipped when it ends at least two days before today and a valid saved file for the same location, with no null values anywhere in it, covers all of its dates. That file can be the month's own file or a wider one, so a narrower run inside a month that is already complete fetches nothing. Otherwise the month is fetched again, because a recent month's last hours may not have been filled in when it was fetched. A new file replaces older files of the same location whose dates lie inside its own; a file that reaches outside the new one is kept, and if it overlaps the new one, `build weather` names both files so you can delete one. The default range starts on 2025-09-30, because the first price day begins at 22:00 UTC that day, and ends on the latest day in `raw/omie`. Any failed request is listed at the end and the command exits non-zero.

`build weather` reads `prices_15min.parquet` and the raw weather files. It stops with an error if any location has a missing hour, a null value, a duplicate hour or a range that does not cover the prices, if a file has an unexpected model or variable, or if any hour would break the bid-time rule. Otherwise it writes to `$IB15_DATA_DIR/dataset/`:

- `weather_hourly.parquet`: one row per UTC hour and location, for every hour of the price range. Each row describes the hour that starts at `valid_time_utc`. Temperature and wind are the values at that time. Radiation is the mean over that hour; Open-Meteo labels that mean with the hour's end.
- `prices_weather_15min.parquet`: the rows of `prices_15min.parquet`, each with the weather of the UTC hour containing its start, one column per variable and location (`temp_madrid`, `wind100_zaragoza`, `ghi_badajoz`, ...).
- `weather_coverage.json`: model, lead, locations, hours expected and present per location, nulls, units, the smallest margin before the bid deadline and the git commit.

## Perfect-foresight battery value

```
uv run ib15 perfect-foresight    # after `ib15 build`
```

This computes the most a battery could have earned on each delivery day if it had known the day's Spanish day-ahead prices (`price_es`) in advance. The main setting is also run on the Portuguese prices, as a check (see `perfect_foresight_portugal.csv` below). It does this once with the 15-minute prices and once with the hourly benchmark, where charging and discharging power stay constant for each whole hour.

The battery has 1 MW of power and 1, 2 or 4 hours of storage (1, 2 or 4 MWh). Its round-trip efficiency is 88%, split equally between charging and discharging. Every delivery day, including the DST change days, starts and ends empty and is optimised on its own as a linear programme solved with HiGHS. An empty battery at midnight is what a battery that plans one day at a time, without knowing the next day's prices, ends up with. A rule that the day must end half full would make the battery buy energy back late in the evening; an hourly schedule pays more for that than a 15-minute one, so such a rule would inflate the 15-minute uplift. There are three specifications. `main` charges 20 EUR for every MWh discharged as a degradation cost. `no_cost` has no degradation cost. `cap2` has no degradation cost and allows at most two full cycles a day.

The command writes to `$IB15_DATA_DIR/results/`:

- `perfect_foresight_daily.parquet`: one row per delivery day, duration, specification and resolution, with gross revenue, degradation cost and net value in EUR per MW, MWh discharged, full cycles, and the number of periods in which the solution both charges and discharges. Charging and discharging share the 1 MW converter, so together they never exceed 1 MW in a period; a period with both stands for the battery alternating between them within it, which burns energy in the losses and is worth doing only at negative prices. The file also holds the `cost_10`, `cost_30` and `cost_40` specifications that the cost sensitivity adds: no cycle cap and a degradation cost of 10, 30 or 40 EUR per MWh discharged.
- `perfect_foresight_summary.csv`: for each duration and specification, the net and gross value over the whole sample at both resolutions, the 15-minute uplift in kEUR/MW, EUR/MW a day and percent, the degradation cost at both resolutions, and the mean cycles a day. A percent uplift is empty (NaN) when the hourly total is zero.
- `perfect_foresight_cost_sensitivity.csv`: the same columns for the setting without a cycle cap at degradation costs of 0, 10, 20, 30 and 40 EUR per MWh discharged, one row per duration and cost. The 20 and 0 rows are the `main` and `no_cost` rows of the summary, taken from the same solves.
- `perfect_foresight_uncertainty.csv`: a 95% interval for the 15-minute net uplift of each duration and specification in the summary, in EUR/MW a day and in percent. Each row is one duration, specification and statistic, with the number of days, the summary's value (`estimate`) and the bounds of the interval (`ci_low` and `ci_high`). The method is described below.
- `perfect_foresight_portugal.csv`: the same comparison on the Portuguese price (`price_pt`) for the `main` specification only. There is one row per window, duration and market (`es` or `pt`), with the window's first and last day (`start`, `end`), the summary's columns and the 95% intervals of the net uplift in EUR/MW a day and in percent (`net_uplift_eur_per_mw_day_ci_low` and `_ci_high`, `net_uplift_pct_ci_low` and `_ci_high`). The `full` window covers every day; its `es` rows are the `main` rows of the summary and its uncertainty file, from the same solves. The `oct_nov_2025` window covers 1 October to 30 November 2025, the days of the `oct_nov_2025` window of `one_cycle_spread.csv` (see "Exploratory analysis"), so the battery model's uplift can be set beside the spread-based one over the same days. A window the data do not reach has no rows. Within a window both markets are resampled on the same days.
- `perfect_foresight_meta.json`: the battery parameters, the degradation cost and cycle cap of every specification in the daily file, the cost grid of the sensitivity, the dates covered, the bootstrap settings, the solve time and the git commit. `portugal_spec` names the specification solved on the Portuguese price, `portugal_windows` gives the dates of each window of the Portuguese file, and `portugal_price_agreement` compares the two prices over every quarter-hour: the share of quarter-hours where the Portuguese price equals the Spanish one, the mean absolute difference between them in EUR/MWh, and each market's mean within-hour spread (the highest minus the lowest of an hour's four quarter-hour prices, averaged over all hours).

The intervals come from a circular moving-block bootstrap over days. Each of 10,000 resamples joins blocks of 7 consecutive days, each block starting on a randomly drawn day and running on from the last day of the sample to the first, until the resample has as many days as the sample. Blocks keep the dependence between nearby days, such as a run of windy or sunny days. On each resample the statistic is computed the same way as the summary computes it: the uplift a day is the mean over the resampled days, and the percentage is the ratio of their sums. The interval runs from the 2.5th to the 97.5th percentile of the 10,000 values. The block length, the number of resamples and the seed were fixed in advance, so every run gives the same intervals. Every duration and specification is resampled on the same days. A bound is empty (NaN) when the hourly total is zero on some resample. The intervals are approximate and depend on the 7-day block length: blocks keep dependence within a week but break it at a lag of seven days and beyond, which the overlapping forecast windows can create. The block length has not been varied, so the intervals should not carry a borderline significance claim on their own.

Every file is first written to a temporary `.part` name. Once all of them are complete, each previous file is moved aside to a `.prev` name, the new files are renamed into place, and the `.prev` files are deleted. A file that another program holds open, such as a CSV open in Excel on Windows, cannot be moved aside, so the run stops with an error naming that file before any new file is in place. On any error the files already moved aside are moved back and the `.part` files are removed, so a failed run leaves the previous results as they were. If a run is killed part way through, the next run that reaches the write step, before it writes its own files, moves the `.prev` files it finds back into place, or deletes them if the killed run had already put all its new files in place. Nothing is written if any day fails to solve.

## Exploratory analysis

```
uv run ib15 eda    # after `ib15 build`, `ib15 build weather` and `ib15 perfect-foresight`
```

This writes the tables and figures that describe the data and where the 15-minute value comes from to `$IB15_DATA_DIR/results/eda/`. It checks every input before it writes anything, and stops with an error if `prices_15min.parquet`, `prices_hourly.parquet`, `weather_hourly.parquet` or `perfect_foresight_daily.parquet` is missing, or if `perfect_foresight_cost_sensitivity.csv` exists without the columns figure G plots (`duration_h`, `cost_eur_per_mwh`, `net_uplift_pct` and `net_uplift_eur_per_mw_day`). The outputs replace the previous ones all together or not at all, in the same way as the perfect-foresight results, so a failed run leaves the previous tables, figures and meta as they were. An hour is the group of four consecutive periods of a local delivery day, as in the hourly benchmark, and its within-hour spread is the highest minus the lowest of its four quarter-hour prices. National mean weather is the mean of the ten locations at each UTC hour. Uplift is the 15-minute net value minus the hourly net value of the `main` specification. All correlations are plain Pearson coefficients and are descriptive only.

- `price_summary.csv`: distribution of the Spanish price at 15 minutes and in the hourly benchmark.
- `within_hour_spread.csv`: within-hour spread overall and by month (mean, median, 90th percentile, share of flat hours) and the mean absolute deviation of a quarter-hour from its hourly mean.
- `uplift_by_month.csv`: net value at both resolutions and the uplift per month and duration, with that month's mean spread and mean price.
- `uplift_concentration.csv`: per duration, the share of the total uplift from the top 10% and 25% of days, the share of days with no uplift, the median and mean daily uplift, and the correlation of daily uplift with the day's mean spread and its price range.
- `one_cycle_spread.csv`: for each market (`es`, `pt`), over October and November 2025 and over the whole sample, the mean daily one-cycle spread of a 1-hour battery at 15 minutes (mean of the day's four highest quarter-hour prices minus mean of its four lowest) and at hourly resolution (highest minus lowest hourly price), and the 15-minute uplift as the ratio of the two. It is a spread-based reconstruction consistent with Rystad Energy's published description of its estimate of the 15-minute gain (a 1-hour battery, one cycle a day, perfect foresight), for comparison with the battery model. Rystad does not state how it treats losses, wear or the order of charging and discharging; this measure assumes no round-trip losses, no wear and no requirement that charging comes before discharging. The battery model's uplift over the same days, for both markets, is in the `oct_nov_2025` rows of `perfect_foresight_portugal.csv`.
- `weather_summary.csv`: mean, standard deviation, minimum and maximum of each weather variable at each location.
- `forecast_motivation.csv`: autocorrelation of the price and of the within-hour deviation at lags of one and seven days, and correlations of the price, the within-hour spread and the within-hour slope (last quarter minus first) with the national mean weather. The slope is compared with the change in the weather across its hour. For temperature and wind, which are values at the start of each hour, that is the next hour's value minus this hour's. For radiation, which is a mean over each hour, it is half the difference between the next hour's mean and the previous hour's, so that the change is centred on the middle of the hour, as the slope is. The signed within-hour deviation is uncorrelated with the weather of its hour by construction, since the deviations sum to zero within each hour, so the shape is described by the spread and the slope instead.
- Figures, each as PNG and PDF: `fig_a` daily mean price and daily mean spread; `fig_b` average price by quarter-hour of day for each season, with the hourly benchmark of one season as steps (each season pools every year of the sample, so autumn mixes the autumns of 2025 and 2026); `fig_c` mean deviation of each quarter from its hourly mean by hour of day; `fig_d` distribution of the within-hour spread; `fig_e` uplift by month; `fig_f` daily uplift against the day's mean spread; `fig_g` uplift against the wear cost, drawn only when `perfect_foresight_cost_sensitivity.csv` exists (otherwise a `fig_g` left by an earlier run is deleted once the new outputs are in place); `fig_h` price against national mean radiation and wind.
- `eda_meta.json`: the inputs with their row counts and date ranges, the outputs, anything skipped, and the git commit.

## Forecast

```
uv run ib15 forecast    # after `ib15 build` and `ib15 build weather`
```

This forecasts the Spanish price of each delivery day using only public data that was available before the day's bid, lets the battery plan on the forecast, pays it the actual prices, and compares what it earns with the perfect-foresight value on the same days.

Bids for delivery day D close at 12:00 Madrid time on D-1. The forecast for D uses the prices of every delivery day up to D-1, which are public by then (D-1's prices appear at about 13:00 on D-2), and the weather forecasts for D in `prices_weather_15min.parquet`, which `build weather` has checked were issued before the deadline. It uses nothing from D's prices or any later day.

Each day is represented by its 96 local quarter-hours (Europe/Madrid). On the 92-period day in March the missing hour takes the values of the hour before it, and on the 100-period day in October the two occurrences of the repeated hour are averaged; the weather is treated the same way. A forecast is then mapped back to the day's real periods: both occurrences of the repeated hour get the same forecast, and the missing hour is dropped. There are three models:

- `naive`: the price of the same quarter-hour a week earlier for Mondays, Saturdays and Sundays, and a day earlier otherwise. On a public holiday it is the price of the same quarter-hour on the most recent Sunday before it.
- `expert`: one least-squares regression per local hour of the day, refitted every day on the 56 days before D. The window was fixed in advance, not tuned. Each hour's regression pools its four quarter-hours, so it has 224 rows at 56 days. The regressors of a row are an intercept, the price of that row's quarter-hour on D-1, D-2 and D-7, the lowest, highest and last quarter-hour price of D-1, dummies for Monday, Saturday and Sunday, and dummies for the second, third and fourth quarter of the hour, so that the level can differ by quarter. On a public holiday the Sunday dummy is 1 and the Monday and Saturday dummies are 0.
- `expert_weather`: the expert model plus the national mean temperature and 100 m wind speed forecast for that hour of D, with a coefficient for each hour, and two radiation terms with one coefficient each for all 24 hours: the national mean radiation forecast for that hour of D, and the change in radiation across the hour times the quarter's position in the hour (-1.5, -0.5, 0.5, 1.5). Each weather value is the mean of the ten locations. The weather forecasts are hourly, so an hour's four quarter-hours share them; the change term lets radiation tilt the shape within the hour, which an hourly value alone cannot do in a regression that pools the four quarters. The change is centred on the hour in the same way as in `forecast_motivation.csv`: half of the next hour's mean minus the previous hour's. At the first and last hour of a delivery day it is the one-sided difference within the day (the next hour minus this one, or this hour minus the previous one), because the bid-time check of `build weather` covers only the hours of D.

Public holidays are treated as Sundays, the usual treatment in price forecasting; a holiday dummy of its own would have few observations in a 56-day window. This assumes holidays behave like Sundays; it is a simple approximation, not something the data were tested for. The holidays are Spain's national public holidays that every autonomous community and Ceuta and Melilla hold, taken from the yearly BOE resolutions of the Dirección General de Trabajo for [2025](https://www.boe.es/diario_boe/txt.php?id=BOE-A-2024-21316) and [2026](https://www.boe.es/diario_boe/txt.php?id=BOE-A-2025-21667). Holidays that only some communities hold, such as Holy Thursday, 19 March or the Monday after a holiday that falls on a Sunday, are left out. The list is in `forecast.py` and covers 2025 and 2026 only, so the command stops with an error if a day falls outside those years. The day after a holiday follows the ordinary rules. The first evaluation day is the 64th day of the dataset (2025-12-03), the first whose 56-day window has every lag; every model and the perfect-foresight benchmark are compared on the same days from there to the end of the data. The hourly forecast is the mean of each hour's four quarter-hour forecasts, so both resolutions use the same information. An hourly schedule depends only on those means, so averaging also removes some forecast noise at the hourly resolution. The forecast result therefore measures what finer dispatch is worth under these forecasting rules.

The battery is the `main` specification (20 EUR per MWh discharged) at 1, 2 and 4 hours. For each model and resolution, the day's schedule is optimised on the forecast and then paid the actual prices: the 15-minute schedule at the 15-minute prices, the hourly schedule at the hourly prices. The net value is the gross revenue at actual prices minus 20 EUR for each MWh actually discharged. The `perfect` rows plan on the actual prices. The command stops with an error if a forecast earns more than perfect foresight on any day, duration and resolution (beyond 1e-6 EUR/MW), since that cannot happen.

It checks every input before it writes anything. It stops with an error if `prices_15min.parquet`, `prices_hourly.parquet` or `prices_weather_15min.parquet` is missing, if the weather file does not hold exactly the rows and prices of `prices_15min.parquet`, if an hourly price is not the mean of its quarter-hours, if the days are not consecutive, or if there are fewer than 120 days (the longest window of the window check below needs 112 training days, each with lags back 7 days). It writes to `$IB15_DATA_DIR/results/forecast/`, replacing the previous files all together or not at all, in the same way as the perfect-foresight results:

- `forecasts_15min.parquet`: one row per 15-minute period of the evaluation days, with its UTC start, delivery date, period, actual price and each model's forecast.
- `forecast_errors.csv`: per model, the mean absolute error and root mean square error at 15 minutes and at the hourly resolution, and the mean absolute error of the within-hour deviation (a quarter-hour's price minus its hour's mean, forecast against actual). The 15-minute uplift comes from that within-hour shape. The last column, `mean_daily_kendall_tau`, is Kendall's tau-b between the forecast and the actual prices of each day's periods (`scipy.stats.kendalltau`), averaged over the days. A day on which the forecast or the actual price is constant has no tau: it is left out of that mean, and it would make the model's `spearman_regret_tau` in `forecast_regret_drivers.csv` empty (NaN). No such day occurs in the sample. The tau measures how well the forecast orders the day's prices, regardless of their level. The schedule also depends on the size of the price differences, since a trade must cover the round-trip losses and the wear cost.
- `forecast_dm_tests.csv`: Diebold–Mariano tests of `expert` against `naive` and of `expert_weather` against `expert`, on each day's mean absolute 15-minute error. The variance is Newey–West with Bartlett weights and a lag of 7 days, and the p-value is two-sided from the normal distribution. Each row gives the number of days, the mean loss difference (first model minus second, so negative favours the first), the statistic, the p-value and the Newey–West lag. The tests compare price errors, not battery value. The p-values are approximate: the models are refitted on overlapping 56-day windows, which can make the daily losses depend on each other over more than the 7-day lag. As a check, each test is repeated at lags of 14 and 28 days; the main result is the lag of 7.
- `forecast_value_daily.parquet`: one row per evaluation day, duration, model (`perfect`, `naive`, `expert`, `expert_weather`) and resolution, with gross revenue, wear cost and net value in EUR per MW and the MWh discharged, all at actual prices.
- `forecast_value_summary.csv`: per duration and model, the net value, gross revenue and wear cost over the evaluation days at both resolutions in kEUR/MW, the net value as a percentage of perfect foresight at the same resolution, and the 15-minute uplift (15-minute net minus hourly net) in kEUR/MW, in EUR/MW a day and as a percentage of the perfect-foresight uplift. A forecast's uplift can be negative, and its percentage can exceed 100. A forecast's uplift equals the perfect-foresight uplift plus what the forecast loses against perfect foresight at the hourly resolution, minus what it loses at 15 minutes. So a forecast that plans the hourly battery badly can show a larger uplift without forecasting the within-hour shape any better.
- `forecast_uncertainty.csv`: 95% intervals for the summary's main figures, with the same circular moving-block bootstrap as the perfect-foresight intervals (blocks of 7 days, 10,000 resamples, a fixed seed), over the evaluation days. Per duration and model (`perfect`, `naive`, `expert`, `expert_weather`) it gives the net value as a percentage of perfect foresight at 15 minutes and at the hourly resolution, the 15-minute uplift in EUR/MW a day and the uplift as a percentage of the perfect-foresight uplift. Per duration it also gives the difference in uplift a day between `expert` and `naive` and between `expert_weather` and `expert` (rows named `expert minus naive` and `expert_weather minus expert`). Each row is one duration, model and statistic, with the number of days, the summary's value (`estimate`) and the bounds (`ci_low` and `ci_high`). Every model and resolution is resampled on the same days, so the intervals for the differences are paired. The percentages are recomputed on each resample as ratios of sums over the resampled days, as the summary computes them, never as means of daily ratios. The `perfect` rows' percentages are 100 by definition.
- `forecast_regret_drivers.csv`: how well each day's forecast errors track the value the battery loses. The daily regret is the perfect-foresight net value minus the model's net value at 15 minutes, in EUR/MW. Per duration and model the file gives the Spearman correlation across days between the regret and the day's mean absolute 15-minute error (`spearman_regret_mae`), and between the regret and the day's Kendall tau (`spearman_regret_tau`). The `pooled` row of each duration stacks the three models' days, so `observations` is three times `days` there. A larger error should go with a larger regret and a higher tau with a smaller one, so the first correlation is expected to be positive and the second negative. These correlations are descriptive.
- `forecast_window_sensitivity.csv`: a check of the 56-day window. The `expert` and `expert_weather` models are refitted on windows of 28, 56 and 112 days and all compared on the same days: the days the 112-day window can forecast, from the 120th day of the dataset. Perfect foresight is computed on those days too. Per duration, model and window it gives the number of days, the mean absolute 15-minute error, the net value as a percentage of perfect foresight at 15 minutes and at the hourly resolution, and the 15-minute uplift in EUR/MW a day and as a percentage of the perfect-foresight uplift. The 56-day rows differ from the main results only because they cover fewer days. With 28 days, each hour's regression estimates 13 coefficients (15 with weather, besides the two radiation coefficients shared by all hours) from 112 rows, so its forecasts are noisier, and noise in the within-hour shape costs more at 15 minutes than at the hourly resolution, where four forecasts are averaged. The main results stay at 56 days, on their own evaluation days, because that window was fixed before any result was seen. On the common days the 112-day window has the lower error and the higher capture at both resolutions for both models and every duration, so the 56-day capture is not the best these models can do. Its uplift is not higher in every case.
- `fig_example_day.png` and `.pdf`: one evaluation day that shows the method, in the style of the exploratory figures. The day is the evaluation day with the median perfect-foresight net uplift of the 1-hour battery (`main` specification, 15-minute minus hourly net value), picked by that rule in the code (ties go by date; with an even number of days, the lower of the two middle days). The top panel shows the day's actual 15-minute prices, their hourly means and the `expert_weather` 15-minute forecast; the bottom panel shows the net power (discharge minus charge, MW) of the 1-hour battery's perfect-foresight 15-minute and hourly schedules. Both use local Madrid time. The chosen date is in `forecast_meta.json`.
- `forecast_meta.json`: the timing rule, the window, each model's regressors (for `expert_weather`, those with a coefficient per hour and those shared by all hours), the estimation method, the definition of the radiation change, the holiday rule, dates and sources, the evaluation dates and count, the Diebold–Mariano settings and the lags of its check, the windows and evaluation dates of the window check, the bootstrap settings, the definitions of the daily Kendall tau and of the regret correlations, the battery specification, the date and rule of the example day, the forecast and solve times and the git commit.

## Method notes

Facts behind the code that the sections above do not state.

OMIE files (`src/ib15/omie.py`):

- A file is latin-1 text: a `MARGINALPDBC;` header line, then rows `year;month;day;period;price_PT;price_ES;` in EUR/MWh, then a `*` trailer line.
- Periods count from local midnight, Europe/Madrid. From 2025-10-01 a period is 15 minutes, so a day has 96 periods (92 or 100 on DST change days); before that a period was one hour.
- Versions seen so far go up to `.3`; `download omie` tries up to `.9`. A day already saved at version v asks for v again; if v is no longer served it tries v+1 to 9. A new day tries 1 to 9. Days more than one day after today (Madrid) are not requested.
- The fetch function returns the body, or None on HTTP 404; any other failure raises and is reported for that day.

Price dataset (`src/ib15/dataset.py`):

- A period's UTC start is local midnight in UTC plus (period - 1) × 15 minutes, which stays correct on DST change days.
- In `prices_hourly.parquet`, an hour is a group of four consecutive periods from local midnight and `period` is the 1-based hour index.
- `build` lists every problem it finds, not only the first.
- `missing_periods` and `duplicate_periods` in `coverage.json`, and `nulls` in `weather_coverage.json`, are always 0 or empty, because validation rejects any dataset that has them. They are recorded so the files state it.

Battery model (`src/ib15/battery.py`):

- In each period t the battery charges c_t and discharges d_t MW, each between 0 and 1 MW, with c_t + d_t ≤ 1 MW.
- Stored energy: s_t = s_(t-1) + η c_t Δt - d_t Δt / η, with η = √0.88 for charging and for discharging, 0 ≤ s_t ≤ capacity, and s = 0 (empty) at the start and end of the day. `energy` in a solved day is s at the end of each period.
- Objective: gross revenue Σ p_t (d_t - c_t) Δt minus the degradation cost of each MWh discharged at the grid side (Σ d_t Δt).
- The hourly case decides one c and d per hour at the hourly price, so its schedule is feasible at 15 minutes and earns the same there.
- A period counts as charging and discharging at once when both exceed 1e-6 MW. With no degradation cost some of these are the solver's tie-breaking: in a zero-price period, doing both leaves the objective unchanged.
- A percentage is empty (NaN) when its reference total is within 1e-6 EUR/MW of zero, so solver noise around zero does not give a huge percentage. This applies to the perfect-foresight uplift and to the forecast summary's shares of perfect foresight.
- A `.prev` file that cannot be deleted after a run has put its new files in place is deleted by the next run.

Weather timing (`src/ib15/weather.py`):

- Source: `https://previous-runs-api.open-meteo.com/v1/forecast`. Its docs (https://open-meteo.com/en/docs/previous-runs-api, read 2026-11-07) say past forecasts are "aligned to fixed lead-time offsets of 1-7 days"; `_previous_day1` "returns the value predicted 24 hours before valid time", and `_previous_day2` the value predicted 48 hours before.
- The `ecmwf_ifs025` archive covers 2025-09-29 onward with no gaps at the ten locations (checked 2026-11-07).
- What a `_previous_day2` value is, checked on 2026-11-04 against the Single Runs API (`single-runs-api.open-meteo.com`, `&run=`): IFS 0.25° open data is 3-hourly at these leads (https://open-meteo.com/en/docs/ecmwf-api: "3-Hourly, 6-hourly after 144 hours"; a run every 6 hours). At a 3-hourly valid time v the value is that of the run started at floor_6h(v - 48 h), the latest run with a lead of at least 48 h (48 to 53 h).
- Open-Meteo interpolates the hours in between after that selection, from the 3-hourly `_previous_day2` series (Hermite, two points either side; 41 of 42 hours reproduced to 0.05 °C). So hour t uses 3-hourly points up to floor_3h(t) + 6 h, which can come from a run newer than t - 48 h.
- When a run is public: ECMWF releases 0.25° open data "at the end of the real-time dissemination schedule" (https://www.ecmwf.int/en/forecasts/datasets/open-data). The files of the 00 UTC runs of 2026-11-05 to 07 on https://data.ecmwf.int/forecasts/ are stamped 07:34 UTC (12 UTC run: 19:34). Open-Meteo states an "additional delay of 2 hours compared to the real-time IFS dissemination" (ecmwf-api docs; real-time steps 48 to 57 go out at about 06:00 UTC). The code takes a run as public 8 hours after it starts.
- The bid deadline for day D is 10:00 UTC on D-1 in summer time and 11:00 UTC in winter time. The latest run any hour of D uses is the 00 UTC run of D-1 (the late UTC hours of D interpolate towards the points at 00 and 03 UTC of D+1), public by about 08:00 UTC, so the rule holds for every hour of D, DST days included, with about 2 hours to spare in summer. `_previous_day1` fails it.
- A row reads two labels: temperature and wind at its hour H, radiation at H + 1 h ("averaged over the past hour", previous-runs docs). The newest run behind a label does not rise steadily with the label: at 20 UTC, label 20:00 interpolates towards 00 UTC the next day (run 00 UTC D-1), while label 21:00 is a grid point (run 18 UTC D-2). So the check takes the newer run of the two labels.
- The ten locations are demand centres, wind areas and solar areas of mainland Spain.
- A response gives its 0.25° grid cell, whose centre is at most about 0.18° from the requested point; a cell more than 0.25° away is rejected.
- A value outside a plausible range fails validation: temperature -40 to 60 °C, wind speed 0 to 100 m/s, radiation 0 to 1500 W/m².

Forecast (`src/ib15/forecast.py`):

- A holiday is kept when every one of the 19 columns of the annex of the Dirección General de Trabajo's yearly resolution marks it `*` (national, not substitutable) or `**` (national, not substituted by the community). 2025: Resolución de 15 de octubre de 2024, BOE of 18-10-2024. 2026: Resolución de 17 de octubre de 2025, BOE of 28-10-2025.
- The annexes list no Sundays. 12 October 2025, 1 November 2026 and 6 December 2026 fall on a Sunday; they are national holidays no community can substitute (art. 45.1 of Real Decreto 2001/1983, BOE-A-1983-20906), so they are on the list, and treating them as a Sunday changes nothing.
- Left out because some communities do not hold them: Holy Thursday (17-04-2025, 02-04-2026; not in Cataluña or the Comunitat Valenciana), 19 March and 25 July, the Mondays after a Sunday holiday (13-10-2025, 02-11-2026, 07-12-2026; only some communities moved the rest day there), and the communities' own holidays (Easter Monday, 26 December and the regional days).
- The Newey–West variance uses Bartlett weights 1 - k / (lag + 1); at lag 0 it is the variance with divisor n.
- Why one regression per hour rather than per quarter-hour: with 96 separate regressions of 56 rows each, the estimation noise of neighbouring quarter-hours is independent, so the 15-minute forecast gets a within-hour zigzag that is not in the prices. The 15-minute battery trades on it, while the hourly mean averages it out, which biases the comparison of the two resolutions. Pooling an hour's four quarters leaves the within-hour shape to the quarter dummies, each quarter's own lagged prices and the radiation change term.
- Why radiation has one coefficient for all hours: slots are local clock time, so at a clock change an hour moves to another UTC hour and another position of the sun. With a radiation coefficient for each slot or hour, a slot that was dark through the whole window, such as 19:00 in winter, has a coefficient fitted to near-zero values only. In the per-quarter-hour model this replaces (96 regressions, each with its own radiation coefficient), the 19:00 quarter-hour's coefficient extrapolated to a forecast of about -441 EUR/MWh on 29 March 2026, when 19:00 moved from 18 to 17 UTC and its radiation forecast rose from about 0 to about 147 W/m², against actual prices near 0. On 25 October 2026 the 10:45 quarter-hour, moved into the sun by the change back, gave about -86 EUR/MWh. A coefficient shared by all hours is fitted on the radiation of every hour of the window, mostly daylight hours, so it is identified whatever hour the clock puts the sun in. Temperature and wind vary in every hour, so they keep a coefficient for each hour.
- The shared and per-hour coefficients are the least-squares fit of one regression over all 24 hours. It is computed in three steps (Frisch–Waugh–Lovell): each hour's own regressors are partialled out of the radiation terms and the price, the shared coefficients are fitted on the pooled residuals, and each hour is then refitted on the price minus the radiation terms.

Exploratory analysis (`src/ib15/eda.py`):

- An hour is flat when its spread is below 0.005 EUR/MWh: prices have two decimals, so a smaller spread means the four quarter-hours are equal.
- A daily uplift below 0.01 EUR/MW counts as zero, since both resolutions are solved to HiGHS tolerances.
- The top 10% and 25% of days are rounded up to whole days.
- A 100-period DST day has 25 hours.
- An autocorrelation at a lag of whole days pairs the same local quarter-hour, except across a DST change, where the pair is one hour off.
- The `oct_nov_2025` window of `one_cycle_spread.csv` is the first two months of 15-minute prices, which came before Rystad Energy's estimate of 10 December 2025.
- In `fig_b` the hourly steps belong to the season whose profile has the most within-hour shape. In `fig_e` a month the sample covers only in part is labelled with its number of days.
- Figures use a light palette, since the paper is printed on white, with series colours in a fixed order; they are 6.5 inches wide (one text column) at 300 dpi.
